# Reality Bias First Paper R Plan v6.0 — Two-Stage Plan with Cross-Layer Generality

Date: 2026-09-25  
Status: **FORWARD / DESIGN-FROZEN / STAGE-I EVIDENCE IMMUTABLE / STAGE-II EXECUTION AUTHORIZED AFTER ADAPTER GATES**  
Predecessor: `docs/R_Plan_v5.9.md`

## 0. Planning rule

This file keeps the first-paper programme in **one planning lineage but two distinct execution stages**.

It does **not** reinterpret the historical R labels as a strict sequence.

```text
Stage I — R-series foundation
    natural emergence -> mechanism -> lineage/inertia -> bounded repair -> semantic synthesis

Stage II — cross-layer generality
    fixed canonical domain -> heterogeneous AI-system layers
    -> common/different authority dynamics
    -> unified observability
    -> minimal discriminating contrasts only where necessary
```

The purpose of Stage II is not to enlarge the old denominator or repeat Stage I.
It asks a different question at a higher system level.

---

# Stage I — R-series foundation

## 1. Frozen role of R2-R9

R2-R9 remain the completed first-stage research foundation:

- **R2-R4**: simultaneous structural views of natural formation and propagation;
- **R5**: one-point local factual-authority challenge / dependence probe;
- **R6**: functional semantic lineage and System Inertia identification;
- **R7**: bounded persistent correction and lineage-addressed repair comparison;
- **R8**: trajectory-first Dynamic CPR semantic synthesis;
- **R9**: innovation boundary, prior-art synthesis, engineering/outlook closure.

Stage I evidence remains frozen under its existing manifests, hashes, reports and released raw-evidence packages.

## 2. Stage-I evidence is not rerun

Stage II MUST NOT:

- rerun R5 across every new architecture;
- recreate R6 as a new subject-model experiment;
- replay the full R7 intervention programme;
- resample frozen Stage-I trajectories to manufacture reproducibility;
- collapse heterogeneous Stage-I evidence into a new pooled prevalence denominator;
- rewrite frozen raw evidence.

R5 has already served its first-stage mechanism role.

Stage II may reuse Stage-I findings as foundation evidence and may add a **minimal discriminating contrast** only when a new system-layer result cannot otherwise be attributed.

## 3. Existing breadth already carried by Stage I

Stage I already provides domain variation through:

- e-commerce discovery history;
- Finance;
- Supply Chain;
- Software Engineering.

These evidence blocks have different denominators and roles and remain separate.

Therefore Stage II does **not** repeat a full domain x architecture Cartesian product.

# Stage II — Cross-Layer Process Reality

## 4. Stage-II research question

Primary question:

> **How do heterogeneous AI-system information and interaction architectures shape the formation, propagation, re-entry and observability of Process Reality?**

Secondary questions:

1. Is Process Reality specific to one multi-agent communication implementation?
2. Which system layers expose distinct C/P/R profiles or healthy-preservation profiles?
3. What object carries authority in each layer?
4. Can one semantic-lineage / authority-observability contract reconstruct these different processes?
5. When two layers differ, is the difference attributable to the system layer rather than the application domain?

Stage II does **not** assume that every layer must show C, P or R.

Different or null results are admissible evidence.

## 5. Canonical domain

Stage II freezes **Software Engineering** as the canonical execution domain.

Reason:

- it is highly observable;
- it naturally supports communication, retrieval, tools, persistent memory, compression and shared state;
- files, calls, retrievals, memory states, summaries, diffs and tests can be frozen;
- it provides a realistic AI-system environment without making AI coding the research object.

The paper-level research object remains **AI-system Process Reality**.

Software Engineering is the controlled testbed, not the theoretical scope.

## 6. Frozen task families

Each new subject condition uses the same three task families.

### T1 — Local interface evolution

A bounded interface / schema / field change with an explicit request to preserve unrelated behavior.

Purpose: observe whether support work or retrieved assumptions acquire extra operational force.

### T2 — Cross-module dependency change

A localized requirement whose legitimate implementation has a known downstream dependency surface.

Purpose: observe how scope, delegation and supporting semantics move through system boundaries.

### T3 — Legacy-path retirement

A repository contains a newer execution path and an older compatibility path that was introduced as temporary or superseded.

The task requests migration / retirement consistent with the current architecture.

Purpose: observe whether historical execution paths regain authority through retrieval, memory, communication, tests, compatibility reasoning or other descendants.

T3 is a normal software-maintenance task.
It MUST NOT prompt the model to produce C/P/R or mention Process Reality.

# 7. Literature anchors frozen before execution

The following anchors are selected **before subject execution**.

They serve two roles:

1. establish that the tested structures are recognized AI-system paradigms;
2. prevent post-hoc framework selection based on which result appears strongest.

They do **not** prove Process Reality.
Stage-II evidence must establish any shared mechanism.

| L3 | cross-agent interoperability | **Agent2Agent (A2A) Protocol Specification v1.0.0** | remote/opaque agent boundary, task/artifact transfer |

Supporting literature does not create an additional subject condition unless a later plan version explicitly authorizes it.

### Frozen literature principle

The new manuscript should use prior work not only to delimit Process Reality, but to establish the AI-system structures across which Process Reality becomes a shared scientific question.

A key Stage-II question is:

> **Performance-preserving transformation need not be Process-Reality-preserving transformation.**

This is a hypothesis to test, not a result to presuppose.

## 9. Fast-execution priority

Three-day target:

### Day 1 — adapters, version lock, smoke gates

- lock exact package / commit / protocol versions;
- implement or bind the seven probe adapters;
- map every probe into the common evidence event model;
- run non-study smoke tests only;
- require evidence completeness before subject execution;
- do not spend subject-model calls on a probe that cannot produce reconstructable evidence.

If a framework cannot pass the adapter/evidence gate within the Stage-II time budget, record:

`ENGINEERING_BLOCKED`

Do not silently substitute an unplanned framework after seeing other outcomes.

### Day 2 — natural subject execution

- execute T1/T2/T3 once per passed probe;
- freeze raw I/O, messages, calls, retrievals, memory states, compressed state, tool/resource responses, task/artifact transfers, file changes and termination state where applicable;
- generate manifests and hashes immediately;
- run structural localization offline;
- do not call a paid semantic evaluator during subject execution.

### Day 3 — semantic audit and minimal contrasts

- reconstruct full semantic lineages for localized candidates;
- adjudicate healthy preservation as well as C/P/R;
- compare carriers across system layers;
- add a discriminating contrast only where attribution remains ambiguous;
- no more than four contrasts in the whole Stage-II first pass;
- produce a cross-layer synthesis report.

# 10. Unified observation contract

Every passed probe must expose enough evidence to reconstruct:

```text
source
-> initial epistemic / authority state
-> carrier
-> transformation
-> downstream read / use
-> decision or execution consequence
-> persistence / re-entry if present
-> final outcome
```

Minimum fields:

- source identity;
- source evidence / authority status;
- carrier type;
- carrier address / event locator;
- semantic transformation;
- receiving actor / system;
- downstream dependency;
- realized scope;
- historical-state relation;
- final outcome relation;
- lineage completeness;
- monitor detection status.

The audit must distinguish:

- ordinary information propagation;
- independent re-anchoring;
- healthy uncertainty preservation;
- semantic descendant continuity;
- C;
- P;
- R;
- cross-penetration;
- censored / unresolved trajectories.

## 11. No outcome-driven relabeling

Before execution, Stage II freezes the following rule:

```text
architecture selected before outcome
task family selected before outcome
observation contract selected before outcome
CPR definitions inherited from frozen Stage I

outcome does not select the theory
```

A probe is scientifically useful if it produces:

- supported Process Reality dynamics;
- a different architecture-conditioned mechanism;
- healthy preservation;
- a null observation under the available exposure;
- or a documented observability / engineering limit.

---

# 12. Minimal contrast policy

Stage II does not recreate R5.

A new contrast is authorized only when two plausible explanations remain after natural semantic reconstruction.

Examples:

- raw context vs compressed context;
- persistent-memory retrieval enabled vs withheld;
- raw retrieved item vs synthesized retrieval path;
- remote artifact adopted directly vs independently re-anchored.

A contrast must:

- alter one local architectural factor;
- use a frozen natural parent where possible;
- stop after the discriminating question is answered;
- not become a new prevalence denominator;
- not trigger a full R5-R7 replay.

---

# 13. Engineering objective

The engineering question is narrower than “one universal repair works everywhere.”

Stage II first tests:

> **Can a common Process Reality observability layer reconstruct heterogeneous authority carriers across communication, retrieval, memory, compression and tool/agent boundaries?**

Required monitor properties:

- carrier localization;
- semantic-lineage reconstruction;
- authority-transition visibility;
- affected-closure derivation where applicable;
- unrelated-state preservation checks;
- historical re-entry detection;
- content-addressed evidence linkage.

Repair portability is secondary.

If repair operators must be architecture-specific while observability remains unified, that is a valid and potentially informative result.

# 15. Analysis geometry

Stage I and Stage II answer orthogonal questions.

```text
Stage I:
change domain while keeping the basic research system relatively stable
-> does Process Reality emerge across semantic environments?

Stage II:
fix one canonical domain while changing major AI-system layers
-> how does system architecture shape Process Reality?
```

The two stages are not a complete Cartesian product.

The paper MUST NOT imply that all domain x architecture cells were tested.

## 16. Cross-layer synthesis targets

The first-pass synthesis asks whether the evidence supports one of several possible outcomes:

### A. Shared mechanism, different carrier

Different layers show a common pattern such as:

```text
authority acquisition
-> semantic transformation
-> functional lineage
-> downstream operational consequence
```

while using different carriers.

### B. Architecture-conditioned mechanisms

Different layers expose materially different C/P/R or preservation profiles.

This is not a failed replication.
It establishes a structure-to-mechanism map.

### C. Layer-specific boundary

Some layers show no supported Process Reality under the frozen exposure.

This narrows the theory and must be reported.

No result category is privileged in advance.

Stage I becomes the compact discovery/mechanism foundation.

Stage II becomes the main breadth/generalization layer.

Target narrative:

```text
natural discovery
-> Process Reality foundation

-> heterogeneous AI-system layers

```

AI coding is a visible testbed, not the manuscript's theoretical protagonist.

The manuscript should not become a coding-agent benchmark or a framework leaderboard.

---

# 18. Budget and stop rules

The Stage-II first pass is deliberately small.

Hard rules:

- canonical domain only;
- three task families;
- at most 21 planned natural subject trajectories;
- at most four discriminating contrasts;
- no full-domain replication before first-pass synthesis;
- no R5/R6/R7 replay;
- no evaluator-driven rerun;
- no run added solely because a desired CPR category has not appeared.

After the first-pass synthesis, further runs require a new explicit plan version stating the unresolved scientific question.

---

# 19. Frozen interpretation boundary

Stage-II first-pass evidence may support claims about:

- cross-layer observation;
- architecture-conditioned Process Reality profiles;
- carrier differences;
- common semantic-lineage observability;
- specific natural mechanisms exposed in the canonical testbed.

It does not by itself establish:

- universal prevalence across all AI systems;
- universal model independence;
- universal provider independence;
- universal domain x architecture invariance;
- a universal repair algorithm;
- production safety guarantees.

---

# 20. Authorization

This v6.0 plan authorizes Stage-II implementation and subject execution only after the corresponding adapter / evidence gates pass.

It authorizes:

- adapter implementation;
- version locking;
- smoke validation;
- up to 21 planned natural subject trajectories;
- up to four minimal discriminating contrasts;
- offline structural and semantic audit;
- append-only evidence freeze and reporting.

It does not authorize:

- mutation of Stage-I frozen evidence;
- unbounded resampling;
- post-hoc framework substitution;
- automatic paid evaluation after every run;
- expansion to four-domain x seven-layer execution;
- claims beyond the frozen evidence boundary.
