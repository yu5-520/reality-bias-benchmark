# Process Reality Report Standard v1.1

Status: **FORWARD ACTIVE REPORTING STANDARD**  
Language: **English only**  
Predecessor: `RB-PROCESS-REALITY-REPORT-STANDARD-v1.0`  
Primary use: Reality Bias / Process Reality experiment and frozen-evidence reports

## 1. Compatibility

v1.1 preserves the visual grammar, evidence-provenance rules, T/E/M/J notation, structural change filter, process/terminal separation and integrity constraints of v1.0.

The scientific extension is limited to two new forward report profiles and one clarified reporting hierarchy:

`local perturbation response -> post-consumption inertia profile -> target-specificity contrast -> terminal outcome separately`

Historical reports finalized under v1.0 remain valid and are not rewritten.

## 2. Reporting principle

Reports are human-readable projections of frozen evidence. They do not create experimental events, reconstruct missing evidence, perform semantic CPR adjudication, authorize reruns or change frozen scientific status.

The primary object remains the realized process.

## 3. Canonical notation

Retain v1.0 notation:

- `Tn` — executed Agent turn;
- `En` — recorded source event;
- `Mn` — recorded message/handoff;
- `Jn` — structural Jump or descendant re-Jump;
- `J0` — selected natural structural root;
- `OS` — one-shot experiment-origin exposure.

Forward specificity reports additionally use:

- `S0` — Natural Reference;
- `S1` — Matched Factual-Field Status Downgrade;
- `S2` — J0-Targeted Authority Withdrawal.

The R7 namespace remains distinct:

- `C1`, `C2`, `C3` refer only to R7 structural-handling conditions.

Do not alias an `S` condition to a `C` condition in a report, even where the underlying one-shot mechanical primitive is shared.

## 4. Evidence hierarchy

All forward reports must keep the following objects separate:

1. raw recorded evidence;
2. structural Jump/lineage derivation;
3. local perturbation response;
4. post-consumption inertia profile;
5. target-specificity contrast, where applicable;
6. terminal outcome;
7. semantic CPR adjudication only when separately authorized and frozen.

A local response must not be presented as system inertia solely because it occurs after an intervention.

## 5. R6 System Inertia Factual Report

### Purpose

Reorganize already-frozen structural evidence under the R6 system-inertia question without creating a new subject run or semantic adjudication.

This profile is appropriate for deciding whether existing frozen evidence justifies a prospective specificity-control experiment.

### Required sections

1. **Scope and evidence binding**
2. **R6 role and analysis origin**
3. **Natural J0 / source-root evidence**
4. **One-shot intervention integrity, if an R5-treated continuation is included**
5. **Natural post-J0 inertia evidence**
6. **Post-consumption treated inertia evidence**
7. **Pairwise inertia readout**
8. **Inertia-dimension matrix**
9. **Directionality / heterogeneity check**
10. **What is directly evidenced**
11. **What is not established**
12. **Eligibility assessment for prospective specificity testing**
13. **Terminal outcome, reported separately**
14. **Interpretation boundary**
15. **Evidence provenance**

### Required distinction

The report must explicitly distinguish:

- immediate/local perturbation response;
- post-consumption system inertia.

Examples of inertia-relevant dimensions include descendant Jump continuation, first descendant distance, direct/indirect inheritance, transfer, root reach/depth, branch/merge/re-entry, cross-Agent spread, path-family structure, state-lineage destination, delayed re-emergence, retrospective return/rebound, post-return inheritance, reconstruction and reconvergence.

### Directionality rule

A valid R6 factual report must not assume that an inertia transition means monotonic expansion or contraction. If matched pairs reverse direction, the report must preserve that reversal and restrict the cross-pair claim to structural reorganization/inertia transition where supported.

### Specificity boundary

A pre-specificity R6 factual report may conclude that existing evidence is sufficient to justify a specificity test. It must not claim that J0-specificity has already been established when no matched factual-field control exists.

## 6. R5-R6 Specificity Validation Report

### Purpose

Report a prospective `S0/S1/S2` experiment testing whether J0-targeted post-consumption inertia is structurally distinguishable from the generic response to the same one-shot factual-status downgrade applied to a preregistered matched non-J0 factual field.

### Required sections

1. **Scientific question and falsification-oriented design**
2. **Frozen source / common-context binding**
3. **Matched factual-field selection integrity**
4. **S0/S1/S2 condition definitions**
5. **S1/S2 mechanical-equivalence audit**
6. **Exposure / consumption / reinjection / persistent-mutation integrity**
7. **S0 natural-reference process**
8. **S1 matched-field process and local response**
9. **S2 J0-targeted process and local response**
10. **Post-consumption R6 inertia profiles for all arms**
11. **Generic uncertainty contrast: `S1 - S0`**
12. **Total J0-targeted contrast: `S2 - S0`**
13. **Primary target-specificity contrast: `S2 - S1`**
14. **Structural distinguishability basis**
15. **Censoring / natural-termination handling**
16. **Process-vs-terminal decoupling**
17. **Claims supported / weakened / unresolved / not established**
18. **Interpretation boundary**
19. **Evidence provenance**

### Matched-field selection integrity

The report must show that S1 was selected before prospective S-arm outcomes were available. Include, where available:

- field-selection contract/schema;
- eligible-pool hash;
- selection-rule hash;
- selected-target hash;
- matching-feature summary;
- exclusion summary;
- outcome-blind attestation.

Do not describe S1 as a `non-Jump field` unless that label is independently supported. Preferred report language is **Matched Factual Field** or **Matched Non-J0 Factual Field**.

### Mechanical-equivalence audit

S1 and S2 must be compared on the frozen intervention mechanics, including:

- operator schema/version;
- from-status class;
- to-status;
- delivery policy;
- direct exposure limit;
- reinjection rule;
- persistent-state mutation rule;
- prompt-visible delta form;
- observation horizon/censoring rule.

The intended experimental difference is target identity, not richer correction content.

### Primary endpoint

The primary specificity endpoint is the **post-consumption R6 inertia profile**, especially `S2 - S1`.

Local activity volume may be reported but cannot by itself establish target specificity.

S1 is not required to have zero effect. A normal factual field becoming `unconfirmed` may legitimately induce additional checking, messaging, writing or rerouting.

### Interpretation matrix

A report should preserve at least the following possibilities:

- **S1 and S2 structurally similar:** generic uncertainty explanation remains viable;
- **S2 distinct from S1 at the inertia level:** supports target specificity under the frozen matched design;
- **S1 stronger than S2:** weakens a simple J0-specificity interpretation;
- **S1/S2 differ in non-monotonic directions:** may still support specificity if the preregistered inertia profiles are structurally distinguishable;
- **no distinguishable response beyond matched variability:** weakens the proposed target-specific mechanism for that design;
- **censored / insufficient horizon:** unresolved, not negative.

## 7. Structural Change Filter v1.1

Retain the v1.0 five levels:

1. surface variation;
2. execution variation;
3. state variation;
4. local structural change;
5. propagated structural change.

For R6/specifity reporting, add a reporting annotation rather than a new level:

- `LOCAL_RESPONSE_ONLY`
- `POST_CONSUMPTION_INERTIA_EVIDENCE`

Only source-backed downstream evidence after the one-shot mark is consumed may receive the second annotation.

## 8. Figures for R6 and specificity

### R6 factual report

Preferred figure sequence:

- panel a: frozen natural J0 and intervention position;
- panel b: natural/control downstream process spine;
- panel c: treated post-consumption downstream spine;
- panel d: multidimensional inertia matrix.

### Specificity report

Preferred figure sequence:

- panel a: common frozen context and target selection;
- panels b-d: time-aligned S0/S1/S2 continuations;
- panel e: R6 inertia-profile comparison;
- panel f: three contrasts with `S2-S1` visually emphasized as primary.

Do not use a single complexity bar as a substitute for topology/inertia evidence unless such a scalar was independently preregistered and validated.

## 9. Evidence provenance extensions

In addition to v1.0 provenance fields, specificity reports should include when available:

- specificity plan hash;
- field-selection record hash;
- eligible-pool hash;
- selected S1 target hash;
- S1/S2 envelope hashes;
- research identity for each one-shot operator use;
- observation-horizon policy;
- specificity comparison schema/version;
- raw-evidence freeze hash;
- structural-derivation hash.

## 10. Claim language

Preferred bounded language for a positive specificity case:

> Under the frozen matched intervention and target-selection rules, the selected J0's acquired factual authority was associated with a post-consumption inertia response structurally distinguishable from the generic response to the same factual-status downgrade applied to a matched factual field.

Do not upgrade this wording into:

- mathematical proof by contradiction;
- universal causal law;
- cross-model/domain generality;
- semantic CPR truth;
- stable monotonic treatment effect;
- reliable controllability.

## 11. Integrity rules

In addition to v1.0 rules, a compliant v1.1 report must not:

- select or replace S1 after inspecting S-arm outcomes;
- hide an S1 response because the control was expected to be inert;
- reinterpret historical R5-MID A/B runs as prospective S conditions;
- relabel existing R7 `C1/C2/C3` as specificity conditions;
- infer `no inertia` from censoring or bounded non-recurrence;
- infer semantic C/P/R from structural specificity alone;
- combine local-response counts and post-consumption inertia into one unvalidated score.

## 12. Version declaration

Forward artifacts using these profiles should declare:

`RB-PROCESS-REALITY-REPORT-STANDARD-v1.1`

Historical v1.0 reports remain frozen under their original standard declaration.
