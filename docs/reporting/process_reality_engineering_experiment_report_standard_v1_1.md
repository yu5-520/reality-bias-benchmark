# Process Reality Engineering Experiment Report Standard v1.1

Date: 2026-09-18  
Status: **FORWARD ACTIVE / TRAJECTORY-SEMANTIC ENGINEERING PROFILE**  
Predecessor: `RB-PROCESS-REALITY-ENGINEERING-REPORT-STANDARD-v1.0`

## Purpose

Engineering reports answer:

> Can a problematic shared-reality structure be localized, content-addressed, semantically scoped, repaired and verified without destroying compatible system memory?

## Reporting principle

Engineering protocol names are not sufficient evidence by themselves.

The report must show the realized multi-Agent process that motivated, executed or verified the operator:

`Structural Path -> Semantic Reading -> Engineering Meaning`

Data structures, state writes, messages, hashes and lineage edges establish the facts. The semantic reading explains what those facts do in the shared process.

1. Engineering Scope and Evidence Binding
2. Structural Repair Anchor

6. Excluded Unrelated Semantic Branches

18. Evidence Provenance / Freeze Boundary

## Agent-trajectory requirement

For each materially different control/repair trajectory, expose where recorded:

- Agent order / turn;
- relevant input premise or shared state;
- message/invocation handoff;
- state object written;
- object status / authority;
- downstream Agent use;
- re-entry / reopen / finalize / censoring;
- supporting event/message/state refs.

Aggregate topology follows the realized path. It does not replace it.

## Semantic reading requirement

Every key path should state:

- which shared reality the Agent accepted;
- what semantic carrier or decision it produced;
- whether the carrier contains independent evidence or descendant interpretation;
- whether authority changed, migrated, persisted or was downgraded;
- whether later Agents reused that carrier;
- what engineering defect or success the path reveals.

## Failed-operator evidence

A failed operator remains part of the engineering report when it reveals a control boundary.

Show expected target behavior, actual Agent behavior, substituted semantic carrier/path, and the operator revision that followed.

## Locality

`local = lineage-bounded relevant structure`, not shallow event distance.

## Preservation

R7 success is not whole-system suppression.

Reports must separate:

- affected/problematic lineage;
- compatible shared information;
- compatible decision state;
- compatible plan state;
- unresolved semantic compatibility.

Normal system inertia may remain useful system memory.

## Selective recomputation

Explicitly distinguish:

`structural recomputation != semantic novelty`

A new state write may reaffirm a compatible decision rather than rebuild a new one.

## Key metrics

Use metrics as support for the path interpretation, including where applicable:

- Repair Anchor precision;
- lineage completeness;
- descendant invalidation / reopen count;
- recomputed refs;
- active Agent count / role re-entry;
- reach / depth;
- branch / merge;
- cross-Agent relations;
- path families;
- preserved compatible structure;
- old-lineage re-entry;
- post-repair watch result;
- provider calls / cost.

## Hard boundaries

- `LINEAGE_GAP` blocks automatic repair.
- A Repair Agent may not invent missing semantic history as fact.
- CPR remains outside R7 unless separately adjudicated in R8.
- Same-parent repeats do not establish population generality.
