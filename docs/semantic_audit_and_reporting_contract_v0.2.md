# Semantic Audit and Reporting Contract v0.2

Date: 2026-09-18  
Status: FORWARD v5 / APPEND-ONLY SEMANTIC INTERPRETATION  
Predecessor: \`docs/semantic_audit_and_reporting_contract_v0.1.md\`

## 1. Core boundary

\`raw evidence -> structural indexing -> scout candidates -> localized semantic audit -> claim/boundary audit -> report\`

System computation establishes structural facts and candidate regions.

Semantic audit interprets proposition meaning, transformation, adoption, support, pool entry, direct consumption, exposure, persistence and recovery.

Neither layer may rewrite the other.

## 2. New v5 semantic distinctions

Audit must distinguish:

\`semantic genesis != semantic transformation != structural support != stable-pool entry != structural exposure\`

and:

\`Detection Surface != Trace Root != Intervention Surface\`

A legacy Jump/J0 may map to one of these objects only through evidence-bound audit.

## 3. Unstable information

The audit may label a proposition \`UNSTABLE_INFORMATION\` when the evidence supports unresolved/limited/conditional epistemic state or materially competing interpretation/goal/boundary pressure.

Unstable does not mean false.

## 4. Escape Structure audit

Escape Structure is not a single semantic-role label on one event.

It is reconstructed from evidence-bound transformations and relations across multiple process objects.

Positive interpretation should identify:

- source proposition/status;
- transformation nodes;
- relation types;
- support/pool candidates;
- downstream proposition/action;
- exact evidence pointers.

## 5. Structural Support

\`STRUCTURAL_SUPPORT\` requires more than structural proximity.

The audit must explain how a proposition/descendant became reusable through system state, dependency, relation or action structure.

Hash ancestry alone is insufficient.

## 6. Stable Shared Information Pool

\`STABLE_POOL_ENTRY\` requires a system-addressable object plus evidence that later consumption can occur without renewed original Agent relay.

Stable means reusable/addressable, not epistemically correct.

\`DIRECT_POOL_CONSUMPTION\` should be audited separately from mere visibility.

## 7. Structural Exposure

\`STRUCTURAL_EXPOSURE\` is a bounded interpretation of where support/propagation becomes sufficiently salient for structural scouting.

It must not be rewritten as semantic origin.

## 8. Driver response

For R5 probes, audit should separate:

- source-level response;
- support-level response;
- pool-level response;
- descendant/constraint response.

A weak source-status propagation result may support a driver hypothesis but does not by itself prove that structure fully replaced information as the causal driver.

## 9. Historical compatibility

v0.1 audit records remain valid under their original schema.

Forward v0.2 uses \`LEGACY_JUMP\` when an old Jump identifier must be referenced without silently asserting the old theory.

## 10. Reporting

Forward reports should explain:

\`source -> transformation -> support -> pool -> exposure -> downstream constraint\`

only to the highest level actually supported.

Structural telemetry remains factual support, not semantic conclusion.

## 11. Authorization

This contract authorizes no provider/evaluator execution, CPR adjudication or active repair.
