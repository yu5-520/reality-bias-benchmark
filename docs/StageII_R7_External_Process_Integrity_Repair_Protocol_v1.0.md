# Stage-II R7 External Process-Integrity Repair Protocol v1.0

Date: 2026-09-26  
Status: **BOUNDARY FROZEN / 21-PATH SOURCE FROZEN / ACTIVE REPAIR NOT YET AUTHORIZED**

## 1. Purpose

Stage-II R7 tests whether an external process-integrity system can locate structural pressure/support relations in frozen heterogeneous AI-system trajectories, construct lineage-bounded repair packages without using the post-hoc semantic answer key, execute any allowed repair only through the studied system's existing native interface and permission boundary, and then observe the complete repaired continuation.

The protocol is not a framework patching exercise.

The engineering principle is:

> **Observe across boundaries; repair only through boundaries.**

The repair system may possess broader observability than any single studied component. It must not therefore acquire broader execution permission than the original system.

## 2. Frozen evidence population

The Stage-II natural source population is exactly the frozen 7 x 3 matrix:

- X1 AutoGen;
- X2 MetaGPT;
- X3 A2A;
- X4 MCP;
- X5 RAG;
- X6 MemoryBank;
- X7 LongLLMLingua;

across T1, T2 and T3.

All 21 natural trajectories are first attempts. No natural trajectory is rerun for R7.

The source binding is:

`configs/stage2_r7_21_path_source_freeze_v1.json`.

The already completed semantic audit remains available only for later validation. It is not a monitor input and it cannot be used to choose, enlarge, merge or prioritize a repair package.

## 3. Order of operations

The Stage-II R7 chain is frozen as:

`boundary freeze`
-> `21-path source freeze`
-> `prefix-causal structural replay`
-> `monitor pressure/support localization`
-> `monitor-derived repair package`
-> `repair boundary preflight`
-> `one native-boundary repair`
-> `repair executor exits`
-> `continued external watch`
-> `independent semantic audit`
-> `frozen natural A vs repaired B comparison`.

No later stage may retroactively modify an earlier frozen object.

## 4. Monitor information firewall

The monitor is a structural system.

It may consume raw execution and observer surfaces, source manifests, the native execution registry, frozen action-contract metadata, task definitions, role definitions and the frozen subject profile.

It must not consume:

- R6-grade semantic audit outputs;
- R6-grade semantic materials;
- post-hoc interpretive audits;
- cross-task/cross-layer semantic synthesis;
- child-report semantic interpretations;
- paper-facing claim registries;
- CPR labels or CPR directional labels.

The machine-readable firewall is:

`configs/stage2_r7_monitor_input_firewall_v1.json`.

The scientific rule is:

> **Semantic audit validates the monitor; semantic audit does not guide the monitor.**

## 5. Prefix-causal replay and no future leakage

Although every natural trajectory is already complete and frozen, the monitor must receive each trajectory in original temporal order.

At prefix `E1..Ek`, the monitor may use only evidence observable at or before `Ek`.

It must not use `Ek+1..End` to decide whether `Ek` is a repair point.

The first prefix that satisfies the registered structural repair gate is frozen as the first eligible repair point for that candidate.

The resulting package records a `prefix_cutoff_ref`.

The remainder of the already-frozen natural trajectory becomes the A continuation. It is not regenerated.

## 6. Structural localization object

The monitor may identify, without semantic CPR labels:

- pressure refs;
- support refs;
- ancestor refs;
- descendant refs already observable inside the prefix;
- affected closure refs;
- preserve refs;
- repair anchor;
- content address;
- detection surface;
- nearest legal repair surface;
- native capabilities required for repair.

The monitor must not claim that a detected object is C, P or R.

CPR interpretation is a later semantic-audit responsibility.

## 7. Framework, protocol and foreign-state immutability

R7 must preserve the scientific object.

The repair system must not modify:

- AutoGen framework scheduling/handoff implementation;
- MetaGPT framework scheduling/memory implementation;
- A2A protocol, SDK semantics, service contract or Agent Card semantics;
- MCP protocol, client/server implementation, tool/resource contract or security boundary;
- RAG corpus, index, embeddings, retrieval structure or retrieval algorithm;
- MemoryBank stored memory, memory index, strength values, recall mechanism or upstream implementation;
- LongLLMLingua model/checkpoint, compression algorithm, compression interface or upstream implementation;
- the frozen natural raw archives.

The repair system also must not directly mutate private native runtime state merely because it is technically reachable from experiment code.

## 8. Detection surface is not repair surface

A problem may be detected in an immutable foreign system.

That does not make the foreign system a valid repair target.

Examples:

- a RAG result may be a detection carrier while the legal repair anchor is the downstream task/process state that adopted it;
- a MemoryBank recall may be a detection carrier while the legal repair anchor is a later process revision or dependent decision;
- a LongLLMLingua transformation may be a detection carrier while the legal repair action occurs at a downstream native process surface;
- an MCP limitation may yield `NATIVE_CAPABILITY_BLOCKED` if no exposed tool permits the required task-state change.

The repair surface must be an object the original system could already modify through its original authorized interface.

## 9. Repair package

Every executable repair package must conform to:

`schemas/stage2_r7_monitor_derived_repair_package_v1.schema.json`.

A package is monitor-derived and must contain:

- source cell;
- frozen prefix cutoff;
- structural monitor evidence;
- pressure/support/ancestor/descendant refs;
- affected closure;
- preserve set;
- repair anchor;
- content address;
- detection surface;
- allowed repair surface;
- native capability requirements;
- explicit forbidden mutations;
- parent reconstruction status;
- repair-gate status;
- post-repair watch contract;
- package hash.

The package contains no CPR label.

## 10. Repair gate

A monitor candidate may resolve to:

- `COMPLETE_FOR_STRUCTURED_REPAIR`;
- `NO_REPAIR_REQUIRED`;
- `LINEAGE_GAP_BLOCKED`;
- `PARENT_RECONSTRUCTION_BLOCKED`;
- `NATIVE_CAPABILITY_BLOCKED`;
- `SAFETY_BOUNDARY_BLOCKED`.

A blocked candidate is an experimental result. It must not be made executable by adding a new framework capability or by bypassing a native boundary.

All candidates satisfying the same frozen repair gate enter the eligible set. The scientific team must not choose only semantically attractive cases after seeing the semantic audit.

If a resource ceiling is later needed, the ceiling and structural ordering rule must be frozen before active provider execution.

## 11. Parent reconstruction

Before a B continuation can run, the exact repair parent must be reconstructable from frozen evidence without stochastic regeneration of the prefix.

The preflight must verify, where exposed by the native system:

- repository/application-state hash;
- message/task/protocol state necessary for continuation;
- remaining execution horizon;
- relevant native session state that is reconstructable from frozen evidence;
- repair anchor identity;
- preserve-set hashes.

Missing required state produces `PARENT_RECONSTRUCTION_BLOCKED`.

It must not be guessed or regenerated by rerunning the model prefix.

## 12. One-package repair geometry

For each eligible package:

A:
`frozen parent -> already frozen natural continuation`.

B:
`same reconstructed frozen parent -> apply package once -> repair executor exits -> native system continues once`.

Rules:

- no A rerun;
- one new B continuation per package;
- no best-of-N;
- no retry to manufacture reproducibility;
- no package rewrite after seeing B;
- no persistent experimental forcing after the package has been applied.

## 13. Continuous external monitoring

The same external monitoring chain spans three phases.

### 13.1 Pre-repair structural scout

Records the causal prefix and the first eligible localization.

### 13.2 In-repair boundary watch

Records every repair operation and verifies:

- requested action;
- target object;
- native interface used;
- original permission availability;
- affected-closure membership;
- preserve-set impact;
- framework/protocol immutability;
- foreign information-state immutability.

Any attempted boundary violation fails closed.

The monitor may police the repair executor. It does not become the scheduler of the studied AI system.

### 13.3 Post-repair native-continuation watch

After the repair executor exits, the native system continues under its original framework/protocol behavior.

The monitor watches:

- old-support re-entry;
- new support emergence;
- authority regeneration;
- scope reopening;
- carrier migration;
- independent re-anchoring;
- repository/application state;
- native calls/messages;
- process closure;
- terminal outcome separately.

The post-repair monitor does not continuously repair new events in the canonical R7 branch.

## 14. Independent semantic audit

Only after monitor localization and the repair package are frozen may the semantic layer enter.

It performs two independent jobs:

1. monitor validation:
   - pressure-point localization;
   - support coverage;
   - closure overreach;
   - closure omission;
   - false-positive / negative-boundary behavior;

2. repair-consequence audit:
   - whether old semantics persist;
   - whether the lineage reroutes;
   - whether authority is independently regenerated;
   - whether a pressure migrates to another carrier;
   - whether unrelated semantics are preserved;
   - CPR interpretation of the repaired continuation.

The semantic audit cannot retroactively modify the monitor package.

## 15. A/B comparison

Comparison is process-first:

- pressure structure;
- support structure;
- lineage/descendant path;
- role/file/call/decision scope;
- preserved unrelated state;
- native-boundary compliance;
- process closure;
- terminal outcome as a separate endpoint variable.

Allowed post-repair structural classes include:

- `COLLAPSE`;
- `REROUTE`;
- `REGENERATION`;
- `MIGRATION`;
- `REENTRY_OBSERVED`;
- `INDEPENDENT_REANCHOR`;
- `PARTIAL_REPAIR`;
- `BOUNDARY_BLOCKED`.

Same endpoint is not treated as same process.
