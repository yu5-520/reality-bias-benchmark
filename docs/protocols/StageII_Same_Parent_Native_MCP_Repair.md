# Same-parent native MCP repair and observed-prefix planning

Status: offline engineering. This is the current supported MCP integration path.
It joins a verified early native parent, observed-prefix source queries, exact
post-proposal authorization, official MCP application writes, host checks,
scripted native continuation and independent-review preparation on one parent.
Autonomous planning, a real repair agent exit and semantic efficacy remain pending.

## Planning evidence window

`PrefixMCPContext` builds a separate graph from evidence whose membership at the
selected native parent is verified. It exposes every observed prefix node and
source query without a depth cutoff. It does not filter a finished trajectory
graph merely by timestamps, remaining budget, archive order or content hashes.

For the frozen experiment-owned host, valid history entries record action counts
and roles. The unchanged passive structural bridge records those envelopes in
turn order. The binding checks each prefix action's actor, kind and sequence,
then matches each native tool action to the original proxy's invocation number,
exact tool request/path and successful response. Missing captures, invalid
envelopes, ambiguous finalization, actor/path mismatches or rejected tool results
fail closed. This correspondence establishes evidence-window membership for
this host; it is not an inferred semantic dependency or universal cross-clock
ordering rule.

The sequence-4 G3-X4-T2 parent includes 5 verified native checkpoints, 12 structural
action records and 9 original MCP invocations. Its graph contains all 434
available observations and 157 node identities. Current and historical prefix
file versions, native host states, inbox messages, model-context snapshots and
wire messages are source-readable. Later checkpoints, invocation 10 onward,
terminal answers, old audit labels and whole future-bearing ledger/event members
are not planner tools. A source pointer into a prefix event is readable without
exposing the remaining event list.

The archive does not contain the exact historical subject-provider prompts and
raw responses. Snapshots and tool messages cannot recreate those missing bytes
or establish complete semantic lineage. The context labels this deficit and
never fills it from later data. A compatibility mapping lets unchanged sealed
field/planning primitives address the current parent; the public catalog
explicitly labels the parent nonterminal and exposes its actual hash.

## Host authorization and native repair

The original broad T2 coding task remains unchanged. Before source inspection,
the host freezes application capabilities and action/value budgets, without
choosing a correct field or replacement value. The actor's inspected proposal
then generates exact fields, versions, values and dependency order through
`ProposalAuthorityCompiler`. A separately retained authorization is consumed
once at native dispatch. Re-sealed payloads cannot replace the retained plan.

The current nonterminal binding supports experiment-owned application fields.
It does not supersede the current answer, inject a process revision or rewrite
historical messages, queue, inbox, budgets, task, protocol or framework state.
Each action checks the whole expected application manifest, reads the current
field through MCP, records an intent, writes through MCP and checks the result
through MCP. Unexpected mutations and missing host verifiers block dependent
steps. A durable recovery journal retains results without automatic replay.

The positive fixture is explicitly scripted: a source-bound conditional launcher
claim proposes changing the unset `CHECKOUT_COMPAT` default in `run.py` from
`on` to `off`. Historical actual launcher use and semantic adoption remain
unknown; the documented primary service already works. This is not an automated
fault localization result or proof of the earliest unsupported authority change.
The controlled verifier checks two payment methods on one cart, not browser or
real-payment behavior. It receives no arbitrary actor-supplied executable code.

## Unchanged official MCP and native host continuation

The binding requires the original frozen SDK commit
`f1b6589088534632fef92238ee9750951e3c0185`, protocol commit
`5f5440bb26a62e2cf3440b92da5a667efa03b267`, clean tracked source and an imported
runtime from that SDK. Its locked dependency environment is materialized with
`uv sync --frozen --no-default-groups`. Native initialization must negotiate the
frozen protocol version and advertise the original checkout server.

`MCPCheckoutProxy`, client, server, transparent wire tee and host `_resume_host`
are reused unchanged. Every read/write traverses the official stdio boundary.
The original X4 proxy starts one native session per invocation; application state
is in the checkpointed checkout and scheduling/mailboxes are in the host. No
private persistent MCP session is invented or patched. Structured MCP results
are decoded only by the repair reader; subject tool results remain exactly as
returned by the original proxy.

The passive observer copies host/application state and exact protocol bytes. It
does not introduce extra native tool calls to monitor file contents. An after-
repair checkpoint retains the original queue, inbox, history, stop state and
remaining budget with the changed application. Four fixed scripted responses
then exercise native tool reading and specialist/entry-agent routing, preserving
history numbering 4 → 8 and budget 60 → 56. Complete after-repair and final host
checkpoints are retained. Generated Python bytecode is excluded consistently
with the native checkpoint application manifest definition; it is not evidence
state or a required reproducible artifact.

An `OFFLINE_REPAIR_DRIVER_EXIT` records script release. It is never relabeled
`REPAIR_AGENT_EXIT`. Native closure from a scripted subject cannot manufacture
the real agent/continuation gate or repair effectiveness. Interrupted attempts
retain partial evidence and existing output directories cannot be resumed or
replayed automatically. Python object binding is an application boundary, not
an OS sandbox or concurrent native-state isolation.

## Evidence and evaluation status

The same-parent graph retains all 434 prefix observations and adds 231 new
source-verified observations: 665 observations / 396 nodes. Four new official
MCP invocations comprise a repair read/write/read and one scripted continuation
read. One application action and its controlled host verification pass. No
host-state repair, real agent or provider/model call occurs.

Independent review preparation uses the unchanged CPR/lineage rules and can
read every historical prefix observation plus the branch sources. It excludes
planner interpretations and write capabilities from its catalog. Its state
remains `PENDING_NATIVE_CONTINUATION`, because no actual repair agent exit or
real subject continuation has occurred. Engineering postconditions are not
semantic review. Old C/P authority, historical re-entry, transformed descendants
and unrelated semantic progression still require independently supported paths.

All 298 retained artifacts reproduce byte-for-byte, including wire bytes,
source captures, complete graphs, exact policies, journal, native checkpoints and
review preparation. This is a separate engineering dataset; its counts are not
combined with older terminal-parent or host-only fixtures. Frozen natural
experiments, semantic audits and original implementation sources remain unchanged.

Next: connect a bounded autonomous planning actor to these prefix source tools,
capture its actual requests/responses and exit, preserve the same native parent,
then use a separately frozen subject-provider/budget binding and independently
evaluate the resulting semantic paths. Missing historical provider evidence
must continue to limit retrospective claims.
