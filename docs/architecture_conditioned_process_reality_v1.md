## Research object and four questions

The first Process Reality paper is the **foundation layer**: the natural e-commerce discovery in which **about 1,520 inventory units** changed factual status, its healthy comparator, Dynamic C/P/R, Functional Semantic Lineage, and the bounded R5/R6/R7 mechanism evidence. The number 1,520 is an inventory value, **not** a count of natural discovery runs. Target foundation space in a future rewritten manuscript: approximately 30–40% of the main text; this is an editorial target, not a result.

The prospective object is **architecture-conditioned Process Reality**: how an interaction substrate affects the authority granted to information, tasks and inherited state during execution. Four questions are registered before collecting new trajectories:

1. Does Process Reality occur across different interaction architectures?
2. How do the dynamic C/P/R profile and their cross-penetration change with architecture?
3. Which carrier conveys semantic authority in each architecture?
4. Can external monitoring, semantic lineage addressing and localized repair work across architectures, with what architecture-specific operators?

The 90 Finance/Supply Chain/Software Engineering natural trajectories, 29 canonical R5 cases, four stronger R6 candidates and four R7 pairs/eight branches remain historical frozen evidence. They are not new architecture samples, are not rerun, and have different denominators. R6 is passive interpretation, not four new subject runs. The frozen-raw release and its SHA-256 manifests remain authoritative.

## Experimental control and observability

Within each domain, hold the task fixture, model configuration, roles/responsibilities, budget policy, semantic rubric and recorder schema fixed **where they can be meaningfully held fixed**. Bind exact hashes and versions of the task, roles, model/provider, prompt policy, architecture adapter, code and audit protocol in each prospective manifest. The interaction instructions necessarily differ by substrate; log the exact prompt/input and treat any unavoidable capability or scheduler difference as a possible co-intervention. Record actual latency, failure and censoring, including inaccessible remote internals. Do not infer architecture causality from an uncontrolled SDK comparison.

All architectures emit the same additive `RB-INTERACTION-EVENT-v1` evidence with stable `event_id`, `event_hash`, raw reference and content address. The adapter surface is `send_message`, `receive_message`, `shared_state`, `delegate`, `handoff`, `tool_call`, `resource_read`, `memory_write`, `memory_retrieve`, `remote_task`, `artifact_return`. Every action is registered in its native source; send/delivery/read/use are separate observations. A message in an inbox or state in a prompt is **exposure**, not proof of semantic use. Preserve full raw payload in the original subject evidence and a hash/locator in the normalized projection. Missing native data must be marked unavailable, never reconstructed as observed. The historical `arena.engine` trace contract and evidence hashes stay unchanged.

## Pilot → formal geometry

Pilot is small, naturally routed and engineering-only for eligibility: (i) useful task completion, including honestly recorded failures/censoring; (ii) end-to-end input/output, message/call/state and boundary evidence; (iii) at least one demonstrably reconstructable `source → carrier → read/use → downstream effect` route **where a route occurs**. Do not select/repeat until C/P/R appears; failure to observe a route is an observability limitation. Pilot is excluded from prevalence and the formal cohort. A scripted offline conformance test checks plumbing only and cannot pass the natural-completion gate.

Only after the adapters and pilot pass, freeze a new manifest for five core architectures × three historical held-out domain fixtures × 6–10 prospective **natural** trajectories per cell (90–150 total). The old Shared Pool 90 cannot silently substitute for the new prospective Shared Pool cells: code, instrumentation or conditions may differ. Any reuse must be a separately labeled historical reference. No outcome-aware retries; a later targeted extension of an ambiguous architecture needs its own prospectively registered amendment, reported separately. Report per-cell denominators and censoring, and treat prevalence as descriptive at this size.

## Trajectory-first semantic audit

For each trajectory, use raw turn/input/output and event locators to reconstruct `source authority → carrier type → authority transition → functional descendants → operational dependence → dynamic C/P/R → cross-penetration → persistence/re-entry → repair surface`. Preserve exact actors, source and descendant quotations/locators, alternate independent support, goal versus realized process, and the affected and unaffected closure. Distinguish direct carry, transformed meaning, mere exposure, independent re-anchoring, unknown remote internals and unsupported authority promotion. Audit old C/P after retrospective R as well as any newly formed C/P. A null/uncertain case remains in the denominator; structural screening must not adjudicate semantics or discard unaudited trajectories.

Select a naturally realized J₀ per eligible architecture on a **carrier with an auditable authority boundary**. Register an architecture-specific operator with the common meaning `withdraw only this carrier's unsupported authority for the next eligible exposure; then exit`. It may be a field status, delegated requirement, remote result, tool/resource trust marker or another supported carrier. Bind the frozen parent, affected closure, exact operator, source hashes, and the no-op/healthy comparison where applicable. Do not rewrite the historical parent or sample repeated exact continuations to manufacture recurrence. R5 remains a local response probe; R6 reconstructs carrier-dependent inertia; repair tests locality and unrelated-state preservation separately.

## Portability gates and claims

Before an architecture enters a portability claim, pass: adapter contract; event completeness; source/carrier addressability; lineage reconstruction; authority-transition auditability; repair locality; unaffected-state preservation; re-entry detection; frozen-evidence integrity. The monitor must report missing fields and blind spots. `UNIFIED_OBSERVABILITY` is possible even when repair operators differ by architecture; a repair success requires evidence of target specificity and preserved unrelated state. Unknown internals or failed conformance count as explicit limits, not negative C/P/R findings.

Do not claim generality, relative CPR profile, intervention response or repair portability until prospective data and semantic review exist.
