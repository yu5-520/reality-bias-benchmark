## 1. Purpose

The first-round replication cohort is now explicitly separated from the ecommerce method-development case.

Ecommerce remains the deep reference domain that produced the theory/engineering method history. It is **not** included in the new prospective replication sample.

The prospective replication cohort contains exactly three held-out domain environments:

- finance;
- supply_chain;
- software_engineering.

The replication principle remains:

> **Replicate the frozen method, not the history of method development.**

The new first-round sample therefore asks whether the final Process Reality observation/control framework transfers prospectively into three different domain semantics without adapting the method to their outcomes.

## 2. Cohort roles

| Domain | Role in first paper | Included in new replication sample |
|---|---|---:|
| ecommerce | method-development / deep-mechanism reference | NO |
| finance | prospective frozen-protocol replication | YES |
| supply_chain | prospective frozen-protocol replication | YES |
| software_engineering | prospective frozen-protocol replication | YES |

The ecommerce evidence remains frozen and methodologically important, but it is not pooled with the new held-out replication trajectories as if all four domains were prospectively sampled under the same history.

## 3. Replication sample geometry

The prospective replication cohort is:

- 30 natural trajectories per held-out domain;
- 3 held-out domains;
- 90 new natural trajectories total.

Each domain is split before execution into two fixed waves:

- Wave A: trials 1-15;
- Wave B: trials 16-30.

The six global waves are:

| Global wave | Wave key | Domain | Domain wave | Trials |
|---:|---|---|---:|---:|
| 1 | finance-w1 | finance | 1 | 1-15 |
| 2 | finance-w2 | finance | 2 | 16-30 |
| 3 | supply_chain-w1 | supply_chain | 1 | 1-15 |
| 4 | supply_chain-w2 | supply_chain | 2 | 16-30 |
| 5 | software_engineering-w1 | software_engineering | 1 | 1-15 |
| 6 | software_engineering-w2 | software_engineering | 2 | 16-30 |

All 90 rows and all six wave identities are preregistered before the first provider call.

The two waves inside each domain are not adaptive sample extensions. They are two frozen execution partitions of one 30-trajectory domain cohort.

## 4. Six-wave concurrent launch

The six waves should be launched under one explicit first-round authorization event.

Operationally they are six independent jobs and may execute concurrently.

They share:

- one exact execution SHA;
- one plan hash;
- one Arena runtime;
- one model/provider config;
- one recording schema;
- one Agent prompt protocol;
- frozen domain fixtures;
- one first-round authorization boundary.

They do not share runtime state or model-call state.

Running all six waves from one authorization event prevents a sequence such as:

`finance-w1 -> inspect result -> modify protocol -> finance-w2`.

If a technical/budget interruption occurs, preserved partial evidence remains frozen and any technical rerun requires append-only recovery records. Semantic or outcome-based reruns are forbidden.

## 5. Unified execution path

```text
S1 Six-wave natural collection
  -> S2 Per-wave raw freeze + structural derivation
  -> S3 Localized semantic audit / case qualification
  -> [if qualified] S4 R5 atomic probe
  -> [if R5 run] S5 R6 full descendant / inertia observation
  -> [if completeness gate passes] S6 R7 semantic-lineage scoped repair
  -> [if R7 run] S7 post-repair watch
```

R2/R3/R4 are simultaneous analysis views over the same natural trajectory, not separate subject experiments.

R5/R6/R7 are conditional case progressions and are never compulsory simply because a domain was sampled.

## 6. S1 — Natural collection

Each wave contains one domain only and 15 natural trajectories.

This makes wave evidence lineage domain-pure:

- finance evidence is never mixed into a supply-chain wave artifact;
- supply-chain evidence is never mixed into a software-engineering wave artifact;
- each domain has two independently frozen execution batches.

Required raw recording remains:

- actual model inputs;
- raw outputs;
- parsed actions;
- message lifecycle;
- invocation lifecycle;
- shared state and metadata;
- model-call event ranges;
- queue/termination state;
- snapshots/journal hash chain;
- usage/cost where available.

No active probe, active repair, CPR adjudication or paid semantic evaluator is part of S1.

## 7. S2 — Per-wave evidence freeze and structural derivation

Each of the six waves receives its own:

- authorization record;
- raw trace ledger;
- journals;
- snapshots;
- summary;
- evidence batch hash;
- structural index;
- candidate ledger.

Raw evidence is frozen before structural derivation.

After all six waves are complete, a first-round registry verifies:

- exact six-wave set;
- same plan hash;
- same execution SHA;
- 90 preregistered rows;
- 30 trajectories per held-out domain when fully preserved;
- wave-level evidence batch hashes.

## 8. S3 — Localized semantic audit and case gate

Structural scouting may find candidate state objects and content addresses.

It may not automatically establish:

- semantic adoption;
- problematic authority;
- R5 eligibility;
- R7 repairability;
- CPR.

Every candidate must pass append-only localized semantic audit before it can become an R5 scientific target.

No qualifying structure is a valid result and must remain visible.

## 9. S4 — R5 atomic probe

If a source-bound natural case is eligible:

- exactly one direct authority withdrawal;
- zero reinjection;
- no experiment-origin persistent mutation;
- then natural continuation.

The three replication domains do not replay older ecommerce operator-development variants.

## 10. S5 — R6 descendant / inertia observation

R6 derives from the frozen R5 branch:

- direct response;
- carrier visibility;
- semantic adoption;
- relation propagation;
- post-consumption inertia;
- topology;
- natural/random variation where matched evidence exists;
- affected-lineage evidence.

Large topology alone is not semantic inertia.

## 11. S6 — R7 final repair operator

If the completeness gate passes, replication cases use the final current repair operator directly:

`Semantic Lineage Package -> affected closure -> compatibility partition -> invalidation/reopen -> selective recompute -> new lineage -> post-repair watch`

Historical replay-based target regeneration is not a replication step.

`LINEAGE_GAP` blocks repair.

## 12. S7 — Post-repair watch

Where R7 runs, record:

- exact old-lineage re-entry;
- authority escalation;
- target rewrite;
- recurrence candidates;
- closure expansion;
- compatible-state preservation;
- stability within the observed horizon.

## 13. Comparison structure

The first paper will have two different evidence roles:

### Development/reference evidence

Ecommerce explains how the method and engineering operator were discovered, revised and stabilized.

### Prospective replication evidence

Finance, supply-chain and software-engineering test the already-frozen method.

Within each held-out domain:

`Wave 1 vs Wave 2`

supports within-domain replication.

Across held-out domains:

`finance vs supply_chain vs software_engineering`

supports cross-domain replication within the same Arena architecture.

The ecommerce case must not be counted as one of four equivalent held-out domains.

## 14. Generalization boundary

This first round can support:

> prospective cross-domain replication within one frozen Free-Agent Arena architecture and one model/provider condition.

It does not establish:

- cross-architecture generality;
- cross-model generality;
- universal occurrence rate across all multi-Agent systems.
