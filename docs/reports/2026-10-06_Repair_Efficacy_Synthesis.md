# Stage II repair-efficacy synthesis

Date: 2026-10-06  
Status: **SEALED**  
Scope: **G3-X4-T2 repair-method mechanism synthesis**

## Main conclusion

The enhanced repair direction is **effective, but not in the simplistic sense of “one repair makes the whole process terminate.”**

The frozen experiments show three different levels of effect:

1. the old local process revision changed the target but regenerated broader implementation work;
2. the source-bound application-route repair sharply reduced implementation expansion while preserving the direct correction, but did not reduce temporal reach;
3. the pending-obligation repair changed the immediate agent behavior to “already satisfied, no change”, but equivalent obligations were later rebuilt by descendant actors and the process again reached the native ceiling.

The combined result is:

> **repair locality can improve before process closure improves. A target can be correctly repaired while the larger authority route remains capable of regenerating the same work through other carriers.**

That is directly aligned with the paper's central distinction between local intervention and downstream process reality.

## A → B → C

| Layer | Intervention | Direct/local result | Downstream result |
| --- | --- | --- | --- |
| A — old local repair | one `state:file-list` process revision | repair boundary preserved | **REGENERATION**; broad implementation path, backend/security/delegation expansion, turn 64 |
| B — enhanced route repair | prefix-only source-bound `run.py` route correction via native MCP | correction persisted; mutation surface narrowed | **MIXED_EFFECT**; no security/delegation/API-file expansion, but review/test activity still reached turn 64 |
| C — live obligation repair | four pending-message supersessions, queue/history/files unchanged | immediate frontend response became “already satisfied, no changes” | **REGENERATION_AFTER_LOCAL_SUPPRESSION**; equivalent obligations reappeared through descendants, turn 64 |

This progression is important because each experiment removes a different easy explanation.

A shows that a precise one-shot local intervention can alter the downstream route without guaranteeing repair.

B shows that better source/route information and a better-targeted native repair can reduce collateral implementation expansion.

C shows that the remaining temporal persistence is not explained solely by the four stale/expanded pending messages: changing them has a real immediate effect, yet their task-pressure semantics are later reconstructed elsewhere.

## What the enhanced repair system has now demonstrated

### 1. Better locality is real

Relative to the old local repair, B reduced subject writes from 5 to 2, avoided the additional `checkout_app/api.py` path, removed security participation and delegation, and retained the repaired application route.

That is an actual repair-system improvement, not merely a better monitor.

### 2. Local semantic authority is repairable

C is especially useful because the intervention changes no application file, history or queue.

The four pending messages were source-bound and visibly superseded. The immediate continuation changed accordingly: where the frozen control still planned additional frontend/API work, the treatment produced an early “the request is already satisfied; no changes were made” finalization.

So the message semantics had operational authority and that authority was successfully changed.

### 3. System inertia is distributed

The process still did not close.

Later actors generated fresh messages asking how to add the payment button and how its UX should work. Those messages were not copies of the four repaired strings. The system reconstructed equivalent task pressure from the remaining state and collaboration process.

This is the strongest new mechanism observation:

> **the repaired semantic can disappear locally while its operational role is regenerated by descendants.**

That is much closer to the paper's dynamic C/P/R formulation than a simple “bad message persisted” story.

## Relation to CPR

These experiments should not mechanically relabel CPR dimensions from event counts. But they provide concrete source-bound paths for the frozen definitions.

For **P**, the original broad task repeatedly becomes additional verification, UX and test obligations even after the requested feature is already present.

For **R**, old task/collaboration authority re-enters after local repair: the exact carrier changes, but the obligation becomes operational again later in the chain.

For **C**, the important observation is descendant transformation rather than literal source copying. A repaired original message does not survive, yet later actors reconstruct semantically equivalent “add/clarify the payment button” content that acquires current operational use.

This is precisely why the paper should keep distinguishing source text, semantic descendants and operational authority.

## What is not demonstrated

The new repair system has **not** demonstrated universal process closure, a success rate, or a product-ready autonomous repair platform.

It also does not need to.

The current paper question is whether process-local repair can be made more precise and what happens afterward. The answer is now empirically richer:

- yes, enhanced route information improves locality;
- yes, targeted obligation repair changes immediate behavior;
- no, neither one alone guarantees whole-process closure;
- the residual failure mode is structured regeneration through linked state rather than a simple write failure.

## Engineering interpretation

The complete node graph matters because the repair target is not necessarily one bad field.

A graph-guided repair system should use the graph to decide **which carriers must be repaired together** and which must only be preserved/observed. Editing every connected node would be wrong; editing only the first visible bad node can also be insufficient.

The experiment therefore supports a route-level engineering principle:

> **repair the smallest evidence-supported set of authority carriers that can prevent regeneration, then exit and observe the untouched remainder.**

That principle is stronger and more specific than “repair from the root” or “repair the last bad output.”

## Paper implication

These two new contrasts can extend the existing bounded-repair section without changing the paper's object.

The clean narrative is:

`old local repair → enhanced route repair improves locality → live obligation repair changes direct behavior → descendant regeneration shows why direct target change is not downstream repair`.

This directly answers one of the manuscript's important distinctions: **direct target change does not mean the subsequent process was repaired.**

It also turns the enhanced monitor/node graph from an engineering appendix into a mechanism instrument: the graph shows where the original carrier was fixed and where equivalent authority later re-entered.
