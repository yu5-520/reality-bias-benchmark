# 1. Scope and Evidence Binding

Stage II fixes one observable environment—software engineering—and exposes three task pressures.

| Task | Frozen user objective | Process pressure |
|---|---|---|
| T1 — version review | Check the project before/after update, test whether the updated version works, address issues found | state construction + interface boundary |
| T2 — feature request | Add a payment button that works with the existing checkout flow | implementation + post-completion review/closure |
| T3 — legacy retirement | Remove old Python compatibility interference so the current version works reliably | functional cut + historical residue + semantic closure |

The seven X conditions are not seven interchangeable competitors. They occupy different layers:

native multi-Agent framework / inter-Agent protocol / tool-resource protocol / retrieval / persistent memory / context compression.

The common scientific inputs are the frozen task files, role roster, subject configuration, initial checkout fixture, execution budgets, and evidence contract. Native execution is preserved before evidence normalization.

# 14. Interpretation Boundary

The strongest bounded interpretation is architectural rather than competitive.

Stage II preserves heterogeneous native execution and then normalizes **evidence**, not the execution architecture. Once the systems run on the same frozen software-engineering objectives, process reality appears through different carriers: role review, exact protocol messages, tool/resource state, retrieval exposure, persistent memory, context transformation, and repository residue.

The report therefore supports the methodological proposition:

> **A terminal functional state is an endpoint measurement; it is not a substitute for the process lineage that produced it.**

The report also preserves the inverse constraint:

> **Observed process difference is not, by itself, evidence of inferior system quality.**
