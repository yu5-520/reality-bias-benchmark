# Source-based application and current host answer branch

## Result and scope

One source-based manual engineering branch on the frozen G3-X4-T2 checkout passes offline integration. A complete coordinated plan is recorded and both native bindings are validated before the first write. It changes one exact application span, verifies its conditional route, then supersedes the experiment-owned host's current answer. The full enhanced graph retains all original observations and relations. There are no model calls, no subject-agent continuation, no natural-subject rerun, no branch promotion and no private product implementation imports.

This is an implementation receipt. It is not an agent-generated route repair, an independent semantic audit, a CPR improvement score, evidence of semantic noninterference or a comparison against local repair. The original broad payment-button task remains unchanged. The application primitive retains its offline-fixture mode; this source-based coordinator uses that primitive for an explicitly manual engineering candidate rather than representing it as a live repair agent.

## Frozen facts and their limits

| Source-supported observation | Interpretation | Limit |
| --- | --- | --- |
| `web/index.html` and `web/app.js` differ between checkpoint-ledger decision sequences 9 and 10 | The captured run changed the frontend | The ledger clock does not establish independent native-clock order |
| The final answer says no code changes were required | A current process account conflicts with captured file changes | No downstream adoption of this account is established |
| README specifies `python -m checkout_app.server` | The documented primary route uses the current service | Browser execution and actual payment processing are not tested |
| `run.py` defaults `CHECKOUT_COMPAT` to `on`; its conditional branch selects legacy | The alternate launcher can select a retired API when the variable is unset | The original run's actual environment/launcher execution is unknown |
| Controlled current-handler POST checks return 200; legacy returns 410 | The two handler contracts differ on the checked cart and methods | This does not demonstrate an end-to-end production checkout or historic launch failure |

The default launcher issue is a conditional engineering repair option, separate from the source-supported account contradiction. The primary direct route already works. Frozen semantic-audit verdicts are not used to produce this diagnosis. Full source locators, version hashes and unknown relations are stored in `route_diagnosis.json`.

## Coordinated branch

| Order | Operation | Hard boundary / preservation |
| --- | --- | --- |
| Before writing | Record combined plan; validate application and host policies against exact source | Original task, graph and terminal checkpoint are bound |
| 1 | Replace the two-character default `on` with `off` in the exact `run.py` span through `HostCheckout.write_file` | Prefix/suffix and all other files retained; explicit `CHECKOUT_COMPAT=on` still selects legacy |
| 2 | Verify controlled launcher selection and current/legacy HTTP handler contracts | Direct current-service responses and explicit legacy mode remain unchanged |
| 3 | Supersede only current host `/answer` through `SoftwareHostCheckpointAdapter.load_state` on a new host instance | Task, budget, stop state, history, queue, inboxes and application files retained |
| Throughout | Append native content, intents, receipts and controlled-probe observations to the enhanced full graph | Original archive and old observations/edges remain immutable; no inferred semantic-adoption edges |

Dependency completion is supplied by the trusted offline coordinator after checks. It is not an untrusted agent API. Policy seals are integrity hashes, not cryptographic authorization signatures; the host separately retains the trusted policy and revalidates source bindings, original task and projected output. The captured host budget of 64 is restored only on the new instance; current constructor limits and framework modules are not modified. No continuation is executed with that budget.

Preflight/dependency failures block subsequent actions. Native postcondition failures retain actual output and receipts. The coordinator retains partial evidence and does not perform hidden rollback. Execution uses sequential version checks, without concurrency isolation or an OS-level compare-and-swap guarantee.

## Evidence and validation

Permanent dataset: `stage2/replication_v2/source_based_host_branch_integration_v1/`.

- Application writes: 1; current host answer supersessions: 1; provider calls: 0.
- Full graph: 1,194 → 1,225 nodes; 31 new observations.
- All 3,343 original observations and 6,514 original edges are retained exactly.
- Historical host records, pending queue and inboxes are unchanged. The old answer remains in frozen source evidence; the revised answer exists only in this new branch.
- JSON receipts, source diagnosis, combined plan and coordination journal are sealed with implementation hashes. Complete graphs and source catalog are compressed losslessly. Raw capture/intents are included in a deterministic archive.
- Eleven new tests check dependency blocks, source drift, widened/resealed policy rejection, historical/private-field rejection, original-task preservation, exact captured-budget restoration, repeated execution and failed-native-output retention. Together with existing route tests: 56 passing tests.
- `scripts/validate_stage2_source_based_host_branch.py` verifies artifact/implementation hashes, native field preservation, route conditions, raw observation sources and graph retention. Its reproduction mode compares receipts, plans, diagnosis, captures and full graphs against a fresh run.
- The work-specific GitHub workflow reproduces both the previous mechanical application integration and this source-based branch without provider credentials. The old diagnostic-harness evidence remains separately validated and unchanged.

Zero-model development outputs are kept outside the permanent dataset. An early constructor-budget incompatibility failed after an application action and retains its partial evidence; it is not included as a semantic repair trial. The final sealed branch validates both native bindings before the first application write.

## Remaining research boundary

The implementation now supports a concrete application/current-account route with native constraints and full monitoring. It still needs agent-generated diagnosis and planning, source-supported semantic/authority adoption checks, monitored native continuation, and a fair same-parent comparison with frozen budgets. Message/private-state writes are unsupported. Runtime historical pressure-point restoration and preservation of unrelated semantic progression have not been demonstrated. Live execution remains disabled until those gates have receipts.

For the paper, this evidence supports the feasibility and traceability of a constrained coordinated branch. It does not yet support claiming that node-graph-guided agents repair more effectively, that the historical failure was caused by the launcher, or that the monitoring mechanism eliminates black-box risk.
